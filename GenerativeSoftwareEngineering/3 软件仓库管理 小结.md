# 3 软件仓库管理 小结

这节课主要讲 Git。小步提交、写清楚 commit message、把一个功能的相关修改组织成 PR，这些做法我已经比较熟悉，所以我想重点记录另外两件事：工程师怎样判断和修正 AI 的产出，以及怎样设计接口，让不同模块能够合作。

## 工程师的品味与学习方式

### 我怎样判断和修正 AI 的产出

最初，我把这节课的一个收获概括为“工程师的品味决定 AI 产出的上限”。后来想得更具体一些，我觉得这句话还可以修正：AI 降低了实现的成本，但我仍然需要判断什么值得做、什么算做好，以及哪些结果需要调整。

模型能够完成任务，有时还能给出比我更充分的解释。但结果是否符合使用者的需要、内容是否清楚、设计是否引入了多余的复杂性，都需要结合具体场景来判断。对 AI 的修正也应该有明确理由：我希望它解决什么问题，当前结果哪里不合适，修改后应该达到什么效果。

这也引出了我更关心的问题：这种判断能力应该怎样培养？

### 从成熟 GitHub 项目的 README 学习

课里给出的一个具体场景，是阅读成熟的 GitHub 项目，留意它们怎样组织 README 和文档。我觉得这个学习入口很值得保留，因为这些材料体现了维护者面对真实使用者时作出的取舍。

读一个 README 时，我可以观察：它怎样介绍项目的用途，怎样帮助用户开始使用，详细资料放在哪里，读者遇到问题时能否找到下一步的入口。例如，为什么有的项目先展示运行效果，再给安装命令？为什么把详细接口说明放到独立文档，而在 README 中只留下链接？

这些安排背后都有对读者需要的判断。如果我只是模仿它的标题层级或排版，就很难学到这部分经验。更值得理解的是：它为什么这样安排，这个安排解决了什么阅读问题，在我的项目中是否也合适。

好的 README 不一定短。一个基础库可能需要解释概念和使用边界，一个命令行工具可能更适合直接给出安装与使用示例。我更愿意用“目标读者能否迅速理解项目、开始使用，并找到所需资料”来判断它的质量。

### 先自己想一遍 再比较差异

**Virtual Implementation 是这节课里我最想记住并实践的学习习惯。** 我的理解是：

1. 先想如果由我解决这个问题，我会怎样做。
2. 再查看成熟项目的实现或组织方式。
3. 找出具体差异，追问对方这样做的理由。
4. 结合目标和约束判断得失，再修正自己的方案。

GitHub 提供真实工程样本，这个方法则帮助我从样本中学到东西。阅读 README 前，我可以先设想自己的内容安排；阅读接口前，也可以先想调用者需要知道什么，再与实际设计对照。

我很认可“先思考，再比较”这一步。这次先写自己的课程总结，再对照原文和讨论中的修正，也是在采用类似的方式。以后我希望把它用到阅读项目和设计模块的过程中，把差异背后的理由留下来，而不仅仅记住一个结论。

## 我想继续理解的接口设计

课程附录里的多 Agent 工作流，是我另一个比较关心的部分。讲者先沿着一条讨论主线确定架构和接口，再让几个 Agent 并行实现。其中的关键，是让各个模块能够依据共同的约定独立工作。

他在 playground 中采用了几种约束：大量计算使用纯函数，程序信息采用统一的表示，真正需要联动的状态集中管理。例如，进度条选中的步骤可以作为共享状态，编辑器高亮和可视化内容再根据这个选择与执行轨迹计算出来。

我目前的理解是，接口定义清楚以后，使用者只需要知道输入、输出和行为约定，就能使用一个模块。模块内部怎样完成计算、使用什么算法，可以由它自己承担。这样修改内部实现时，影响更容易集中在有限范围内，也更适合交给不同 Agent 分别完成。

这里的接口约定比参数类型更广。例如，执行器返回“第 8 步的状态”，还需要说明它指执行前还是执行后的状态。双方即使使用相同的数据类型，也可能因为理解不同而展示出错误结果。错误怎样返回、状态由谁保存、调用是否会修改其他数据，同样需要明确。

不过，我还没有完全回答“怎样才算一个好的设计”。纯函数和少量共享状态是具体手段，“十几行”本身不能证明架构好。我想继续检验的是：

- 别人能否只看接口说明和样例，就正确使用这个模块？
- 修改内部实现时，其余模块是否通常无需跟着改？
- 真正共享的状态由谁保存，哪些信息可以直接计算出来？
- 能否通过接口验证行为，而不用启动整个应用？

README 帮助读者理解项目，接口帮助调用者正确使用模块。对我来说，两者有一个相通的问题：怎样判断对方必须知道什么，并把这些信息表达清楚。

后续我想结合自己的一个真实模块来理解这些问题。先写清楚它承担什么职责、调用者必须知道什么，再模拟一次具体修改，看看影响会扩散到哪里。阅读材料可以先从 John Ousterhout 的 [Modular Design 讲义](https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=modularDesign)开始；界面状态的组织则可以结合 [Thinking in React](https://react.dev/learn/thinking-in-react) 的第 3、4 步来理解。

## 附录 GitHub 自动关闭 issue

这次了解到的一个小技巧，是在 PR 的描述正文中写关闭关键词，例如：

```text
fixed #3
```

这里的 `#3` 指该仓库编号为 3 的 issue。PR 合并到仓库的默认分支，并且仓库启用了关联 PR 合并后自动关闭 issue 的设置时，GitHub 会自动关闭它。`fixes`、`close`、`closes` 等也是支持的关键词。

关闭关键词也可以写在 commit message 中，随提交进入默认分支时触发关闭。普通 PR 评论中的引用不等同于这种关闭关联。具体规则见 [GitHub 官方说明](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)和[自动关闭设置](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-auto-closing-issues)。
