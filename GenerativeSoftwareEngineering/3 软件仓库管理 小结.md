# 3 从 README 到接口：AI 协作中的工程判断

这一讲里，我最想继续琢磨的是 README。说明项目能做什么，给出简单的使用方式，有直观效果时再放几张截图，详细资料留一个入口，我觉得就已经能成为一个不错的项目入口。

简洁的 README 需要判断哪些信息应该先出现、哪些可以留到后面。接口设计也需要类似的判断：调用者需要知道什么，哪些细节可以由模块内部处理。这是我想从 README 继续谈到接口和 AI 协作的原因。

## 从简洁的 README 学习工程品味

讲师提到，有些维护多年的老项目，README 很短，但看完以后，想继续了解的内容都有清楚的链接可以进入。我认同这种简洁：用途说明、简单使用方式、能展示效果的截图，再加上必要的文档入口，就能让读者知道这个项目是否适合自己、怎样开始使用。

阅读这样的 README，可以留意它如何安排第一次使用所需的信息：截图展示了什么效果？安装和使用示例能否让人直接尝试？遇到更复杂的需求，是否容易找到详细说明？

### 把观察变成对 AI 的具体要求

工程品味体现在这些具体取舍里。觉得一个 README 清楚好用之后，还要能说出它为什么好，再把这种判断变成 AI 可以执行的要求。例如，对一个面向首次使用者的工具，可以提出这样的修改要求：

> 开头用一两句话说明工具的用途和运行前提，提供安装命令与一个可直接运行的最小示例。工具有直观效果时，放一张能说明效果的截图。详细参数放到独立文档，README 中保留入口。

这种要求给出了信息顺序、文档分工和可检查的结果。AI 能据此修改，我也能判断修改是否帮助读者完成第一次使用。

简洁仍然要围绕读者的需要。一个基础库可能需要先解释概念与使用边界，一个带界面的工具可能更适合先展示截图。保留多少内容，要看读者能否理解项目、开始使用并找到后续资料。

### Virtual Implementation 的比较过程

**Virtual Implementation 的重点是先形成自己的方案，再与成熟实现比较。** GitHub 提供真实工程样本，这个方法帮助读者理解样本背后的取舍。

1. 根据问题和约束，先构思自己的实现或内容安排。
2. 查看成熟项目的做法，找出具体差异。
3. 追问差异背后的理由，判断它解决了什么问题。
4. 比较各自在当前目标和约束下的得失，修正自己的方案。

以 README 为例，可以先写一份内容提纲，再对照项目的实际文档。重点记录信息顺序、快速上手入口和详细文档分工的差异。向 AI 提问时，也应带上这些具体差异和读者背景，让解释围绕真实取舍展开。

同样的方法可以用于阅读接口：先设想调用者需要哪些能力、必须知道哪些约束，再与项目的接口比较。学习所得应包含采用某种设计的理由，以及这些理由成立的条件。

## 接口设计与多 Agent 协作

接口是调用者正确使用模块时必须知道的全部约定，包括输入输出、数据含义、错误、副作用、使用顺序和必要的性能约束。接口说明足够清楚，模块才更容易被独立实现、使用和验证。

### 明确接口的数据与行为约定

以程序执行器和可视化模块为例，执行器可以接收源码与程序输入，返回执行轨迹 trace。仅约定返回类型是 `Trace` 还不够，还需要说明每一步的数据代表什么。

| 约定 | 需要明确的内容 |
|---|---|
| 输入 | 源码、程序输入，以及执行所需的明确条件 |
| 输出 | 每一步的源码位置、变量值和程序输出 |
| 数据含义 | 一步对应什么操作，记录执行前还是执行后的状态 |
| 错误 | 语法错误、运行错误、执行超限怎样返回 |
| 副作用 | 是否修改输入，是否读取或修改其他模块的状态 |

例如，执行器返回“第 8 步的状态”，可视化模块就需要知道这是第 8 步执行前还是执行后的状态。双方的数据类型即使一致，也可能因语义理解不同而显示错误结果。

可视化模块围绕这套明确的数据契约工作，就无需了解执行器内部怎样解析和运行程序。只要契约保持一致，执行器内部算法的变化通常可以集中在该模块内。

### 用纯函数和明确的状态归属组织联动

纯函数的结果只由输入决定，在相同输入下返回相同结果，计算时不修改外部状态或传入的数据。把画面生成、源码位置查找等计算组织为纯函数，有助于单独验证行为，也减少了模块之间隐含的相互影响。

生成执行轨迹同样需要明确输入。时间、随机数或外部数据会影响结果时，应纳入执行条件或由外部处理，才能使计算结果具有可重复性。

编辑器、进度条和可视化画面需要联动时，可以由一个明确的所有者保存当前步骤 `selectedStep`，其他显示信息根据它与执行轨迹计算：

```text
执行轨迹 + 当前步骤 → 编辑器高亮位置
执行轨迹 + 当前步骤 → 当前变量表
执行轨迹 + 当前步骤 → 菜单按钮状态
```

这样可以减少多份状态之间的同步工作。组件内部的临时状态仍可留在本地；只有需要共同协调的信息才共享。判断设计是否有效，应关注状态归属和变化路径是否清楚，而不是共享状态定义了多少行。

### 先检验接口，再并行实现

多 Agent 协作需要共同的数据和行为约定。架构设计阶段先统一模块职责、接口与状态归属，再验证一条完整交互，例如：

```text
输入程序 → 生成执行轨迹 → 选择某一步 → 编辑器与可视化显示一致
```

这条路径能暴露缺失的数据、含糊的步骤语义和不清楚的状态归属。验证后再按模块分工，各个 Agent 就可以依据接口独立实现，并通过接口检查自己的结果。

评价设计时，可以检查：调用者是否只需阅读接口说明和样例，内部修改是否通常集中在一个模块，共享状态是否有明确所有者，以及行为是否能脱离整个应用单独验证。

John Ousterhout 的 [Modular Design 讲义](https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=modularDesign)讨论了接口、深模块与信息隐藏。界面状态的组织可以结合 [Thinking in React](https://react.dev/learn/thinking-in-react) 的第 3、4 步，以及 [Choosing the State Structure](https://react.dev/learn/choosing-the-state-structure) 中对冗余和重复状态的分析来理解。

## 后记彩蛋：GitHub 自动关闭 issue

在 PR 的描述正文中，可以通过关闭关键词关联 issue：

```text
fixed #3
```

`#3` 指该仓库编号为 3 的 issue。PR 合并到仓库的默认分支，且仓库启用了关联 PR 合并后自动关闭 issue 的设置时，GitHub 会自动关闭它。`fixes`、`close`、`closes` 等也是支持的关键词。

关闭关键词也可以写在 commit message 中，随提交进入默认分支时触发关闭。普通 PR 评论中的引用不等同于这种关闭关联。具体规则见 [GitHub 官方说明](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)和[自动关闭设置](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-auto-closing-issues)。
