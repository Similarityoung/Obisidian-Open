使用说明

本稿用中文整理课程第 7 讲，即“需求和架构”的第二讲。正文保留十二个主题，不是视频逐句转录。“我的理解”暂留空，由本人阅读后补充。

这里的“受控中文”指一种写法：一句只讲一个主要意思，直接说明谁做什么，同一概念使用同一术语。它借鉴受控语言的表达原则，不是新的语言标准。

ASD-STE100 是英语技术写作标准。本稿不使用英文正文，也不声称符合该标准。你提出的“80%”作为清晰、简短、一致的风格目标，不作为合规比例。

正文用三个标签区分内容：课程观点复述课堂论证；教学示例说明具体用法；编者说明限定适用范围。技术名称和代码标识保留必要的原名，解释使用中文。

先看主线：变化应该由哪里负责？

问题

这份内容讨论一个贯穿软件开发的问题：需求会变化，系统中的结果又相互依赖。我们怎样知道一项变化应该改哪里？怎样避免同一条规则被写在多个页面、多个字段和多个服务中？怎样在结果变化后说明依据，并重建受影响的结果？

课程先区分两类复杂性。选课容量、先修课和审批是业务本身的困难，架构不能消除它们。重复数据、复制规则和手工同步是实现带来的额外困难，架构可以减少它们。需求和架构的共同任务，是明确哪些决定现在必须固定，哪些选择可以留给未来。

为什么这些技术放在一起？

人不能一次理解程序的全部细节。因此课程依次介绍抽象、分层和共同组合规则。UNIX、关系数据库和互联网不是三段孤立的技术史，而是三个例子：只要接口和责任保持清楚，局部实现就可以变化，其他部分不必全部重写。

MVC、视图模型和 React 把同一个问题带到业务应用和界面：哪些是输入，哪些是由输入计算出的结果，变化应该由哪一层负责？订单、记账和教务审核会跨越较长时间，并且依赖历史事实、规则版本和人工决定。只保存一个状态字段，往往无法说明“这个结果怎样产生”。

贯穿例子：教务审核

成绩和审批记录是事实。培养方案是规则。已通过课程和分类学分是派生结果。成绩更正是新增事实。系统按新事实和适用规则重算当前结果。毕业设计、资产归还和其他特批条件需要分别判断。

可以把这条线写成：事实 → 规则 → 结果 → 新事实 → 重算结果。

课程给出的回答

事件溯源和重放是对此的一种回答，但不是所有系统都必须采用的方案。系统保存已接受的事实和必要的规则版本，再从它们计算当前视图。更正通过追加新的事实表达。重放只重新计算内部结果，不能再次付款、发通知或执行其他外部动作。这样，系统可以检查计算、保留依据，并在输入或规则变化后重建受影响的结果。

本稿的主线不是“从 UNIX 学到事件溯源”，也不是把所有技术归为同一种架构。主线是：把变化、责任、事实和计算依赖说清楚，让现在的结果能够回答“我依据什么得出”。

阅读顺序：四幕

  • 第一幕（第 1—3 章）：先理解复杂性、抽象和解空间，回答“为什么不能把所有决定混在一起”。
  • 第二幕（第 4—6 章）：看 UNIX、关系数据库和互联网怎样用共同规则支持局部变化，回答“不同部分怎样一起工作”。
  • 第三幕（第 7—9 章）：把边界带到 MVC、界面状态和长流程，回答“哪些是输入，哪些是派生结果”。
  • 第四幕（第 10—12 章）：用事实、规则版本和重放处理记账与教务，回答“结果怎样重建、解释和审计”。

阅读每章时，先问三个问题：它处理哪种变化？哪项决定放在哪个边界？结果怎样验证或重建？事件重放实验用于观察“事实 → 规则 → 结果”的变化；它不代表所有系统都应采用事件溯源。

1. 复杂性与架构

课程观点： 软件开发从意图出发，形成规约，再形成实现。意图说明要解决什么问题。规约明确行为和约束。实现把规约变成程序。

这条路径不是唯一的。每次选择都会排除一些可能性，也会留下需要维护的承诺。例如，“方便学生选课”可以采用先到先得，也可以采用志愿排序。

十行程序也有架构。大型系统同样有架构。区别不在于是否画过架构图，而在于代码作出了哪些决定。设计时要问：什么可能变化？变化应该由哪一部分负责？

本质复杂性来自业务问题。选课需要考虑容量、先修课、时间冲突、教室、审批和例外。换成纸笔，这些约束仍然存在。架构不能替业务删除这些约束。

附带复杂性来自实现方式。同一条业务规则可以使用文件或数据库表示，两者带来的管理成本不同。重复保存数据、复制规则和反复同步，也会增加附带复杂性。

需求工作减少对意图的误解。架构工作减少规约和实现中的无谓选择。“容量为 100”仍然不够明确：候补是否占名额？预留名额何时释放？谁可以特批？每项承诺都需要测试和维护。

编者说明： 布鲁克斯用这两类复杂性区分业务本身的困难与表达方式带来的困难。附带复杂性并不次要。团队通常可以通过更清楚的边界减少它。

2. 抽象与层次

课程观点： 人不能同时追踪一个大型程序的全部细节。抽象和分层把整体拆成可以逐层检查的部分。

戴克斯特拉提醒程序员尊重人的认知限制。结构化程序设计使用顺序、选择和重复，让程序的推理过程更容易掌握。

  • 枚举：检查有限的情况和分支。
  • 归纳：用归纳法说明重复过程。
  • 抽象：让调用者依赖接口承诺，不必展开内部过程。

软件设计可以像一串珍珠。每颗珍珠承载一个决定。连接规则把这些决定组合成系统。模块数量不是重点，决定的顺序才是重点。

例如，一层过早把图像规定为“一行一行的数据”，后续层就必须理解行。如果把这个决定留在更低层，上层仍可按“图像”处理。表示细节传播得越少，修改它时通常需要改动的地方就越少。

类把数据和操作组织在一起。对象可以保存状态。子程序通过调用和返回组织控制流。协程可以保存执行位置，暂停后再继续运行。

教学示例： 底层提供链表操作，中层提供离散事件模拟，上层描述车间中的机器和订单。上层可以使用业务概念，不必同时追踪指针、等待队列和模拟时钟。

3. 解空间：固定规则，保留选择

课程观点： 好的架构不必预先选定所有未来功能。它应当定义共同规则，让一类解决方案可以继续生长。这类允许的方案构成解空间。

一个明确的名称可以承载已有知识。讨论“事务”或“选课资格”时，程序员不必每次重新展开全部实现细节。

斯蒂尔关于“让语言生长”的演讲说明了这种设计。语言太小，容易移植，却可能无法完成实际工作。语言一开始就做得太大，又可能迟迟无法交付。可生长的语言通过稳定规则增加能力，扩展与核心能力遵守相同的组合规则。

软件也需要这种性质。今天可以规定数据交换格式，明天再增加处理步骤。今天可以确定接口，之后再替换内部实现。共同协作规则保持明确，局部实现仍有选择空间。

阅读经典设计时，可以问两个问题：它让使用者保留了哪些选择？它用什么规则保证这些选择能够一起工作？

编者说明： 解空间不是推迟所有决定的理由。团队仍要确定输入、输出、错误、权限和组合语义。没有明确契约，使用者得到的不是自由，而是猜测。

4. UNIX：用共同规则组合工具

课程观点： UNIX 的三条原则相互依赖：一个程序做好一件事；程序之间可以协作；程序通过共同接口处理文本流。

文本流连接人、文件和程序。人可以阅读输出，文件可以保存输出，下一个程序也可以读取同一份输出。中间结果可以单独检查。

  • 标准输入承载输入数据。
  • 标准输出承载正常结果。
  • 标准错误承载诊断信息。
  • 退出状态表示执行结果。

这些约定使组合成为可能。选项需要共同形式。-- 通常表示结束选项解析。供其他程序读取的数据，不应随意混入颜色控制码和诊断文字。分隔符也是协议的一部分。

教学示例： 用户把 JSON 数据交给 jq 提取字段，再把结果交给 fzf 选择。选择结果仍可交给另一个命令。设计者提供组合规则，不必预先实现所有用途。

编者说明： 文本不自动等于安全、明确的协议。发送方和接收方仍须约定编码、字段、分隔符和退出状态。文件名或字段中出现换行时，简单按行切分可能出错。

5. 关系数据库：分开逻辑与存储

课程观点： 科德提出的关系模型，减少了物理存储变化对数据使用者的影响。应用描述逻辑关系，数据库管理存储和执行。

图书馆可以记录读者、馆藏和借阅关系。同一组事实可以回答两个问题：某位读者借了哪些书？某册书由谁借走？应用不必为这两个问题各维护一份独立事实。

数据库可以调整索引、数据页或扫描顺序，而不改变查询的问题本身。SQL 提供描述关系和查询的语言。事务组织需要整体处理的状态变化。视图提供当前数据的某种查询结果。

灵活的接口往往会发展出一门语言。UNIX 命令解释器和 SQL 都有语法、语义和组合规则。使用者可以在规则内表达新的需求。

编者说明： 关系数据库不能消除业务复杂性。数据库可以执行约束、协调更新，但团队仍须定义实体、时间、权限和例外。隐藏物理存储，也不表示查询和事务没有性能成本。

6. 互联网：在变化中保持协作

课程观点： 互联网提供连接能力，不预先规定所有上层应用。不同层承担不同责任。

  • 应用层表达应用所需的通信。
  • 传输层提供相应的交付性质。
  • IP 层跨网络传递数据报。
  • 链路层在相邻设备之间传递数据。

如果各层遵守接口，一层可以变化，而不必重写全部其他层。网络可以更换硬件和路径，应用仍然使用原有协议。

RFC 1958 把持续的技术变化视为架构事实。课堂把互联网比作城市：道路和建筑不断变化，共同连接规则让城市仍然可以运行。这种稳定的抽象并不简单，TCP 拥塞控制等内部机制仍需细致设计。

安全远程访问逐渐使用 SSH 替代 Telnet。文件传输和网页访问发展出更安全的方式。SMTP 和 IMAP 仍承担电子邮件通信。共同协议允许局部演化，不要求整个系统同时重建。

编者说明： TCP 连接仍会失败。并非所有通信都使用 HTTPS。互联网的例子也不表示所有系统都需要很多层。只有当职责会独立变化时，分层才有明确价值。

7. MVC：为不同变化分配职责

课程观点： 早期业务系统可以把一次请求映射成一次数据库事务，把页面看作数据的一种呈现。一次选课请求读取数据、检查规则、写入记录，再返回页面。

这种结构适合许多稳定的增删改查业务。增删改查可以配合事务和局部规则，但不会自动保存全部业务历史。当每个页面复制规则时，风险就开始增加。学生入口和管理员入口可能采用不同的容量判断。

Java 网页工具改善了页面生成。Servlet 在 Java 代码中生成 HTML。JSP 允许在 HTML 模板中嵌入服务端代码。JSTL 和表达式语言进一步减少脚本片段。模板更容易维护，不等于业务规则已经有统一归属。

MVC 把责任分给三个部分：

  • 模型：表达领域知识，执行业务操作。
  • 视图：展示模型提供的数据和结果。
  • 控制器：接收用户输入，组织对模型的调用。

教学示例： 课表从列表改成日历，主要改变视图。容量规则变化，应由模型负责。新增管理员入口，应复用已有业务能力，并检查权限。

编者说明： MVC 是关注点分离的思路，不是一种固定框架或文件夹结构。具体边界取决于业务和技术。模型也不只是数据库表。

8. 界面状态：保存来源，计算结果

课程观点： 搜索词、展开的菜单、悬停效果和选中的标签，都影响界面。它们未必属于业务数据库，但仍然是程序状态。

可以把关系写成：界面 = 渲染（业务模型，界面状态）。是否需要持久保存，和是否需要认真建模，是两个问题。

MVVM 把展示状态和行为组织进视图模型。以课程筛选为例，程序保存查询词，再根据课程列表和查询词计算可见课程。不必把筛选结果再作为独立状态保存一份。

Vue 的 computed 追踪响应式依赖。v-model 连接控件值与输入事件。这种局部双向连接，不表示所有数据都可以任意双向流动。组件属性通常仍从父组件传给子组件。

React 根据当前属性和状态描述界面。状态更新请求后续渲染，每次渲染读取当次状态快照。由这些输入计算出的课程列表，不必再变成另一个状态字段。

编者说明： React 不等于 MVVM。两者处理相近的状态依赖问题，但机制不同。不要把框架名称直接当作架构结论。

9. 长流程：仅靠当前状态不够

课程观点： MVC 和增删改查适合许多局部操作。当业务跨越较长时间，并涉及多项规则时，只保存当前状态往往不够。

订单可能经历下单、锁库存、付款、风控、发货、退款和对账。教务流程可能同时涉及学分、毕业设计、资产归还和审批。

一个状态字段可以表示阶段，一组布尔字段可以表示更多细节。但这些字段本身不能解释：当前结果来自哪些历史事实？错误或手工覆盖可能让不同字段相互矛盾。

教学示例： 学生通过后续课程后，先修课成绩被更正。系统需要重新检查相关课程、学分和结论。如果只直接修改部分字段，遗漏的字段就会保留错误状态。

编者说明： 事件溯源不是增删改查的通用替代品。只有历史、审计或重建视图确实有价值时，才值得承担它的存储和运维成本。依赖分析仍需显式建模；事件溯源不会自动生成依赖图。

10. 过去、现在与未来

课程观点： 复式记账要求每笔交易的借方合计等于贷方合计。借和贷是记账方向，不固定等于增加和减少。账本还需维护“资产 = 负债 + 所有者权益”的关系。

借贷平衡只能检查一部分错误。分录即使金额平衡，也可能使用错误科目。原始凭证和业务分类仍需审查。

事件溯源保存已接受的事实记录，再按规则计算当前视图。应当分清三个对象：

  • 事件：记录已经发生的事。
  • 命令：表达希望执行的动作，可能被拒绝。
  • 投影：按规则处理事实后得到的当前视图。

更正应增加新的记录，不应悄悄抹去原有依据。未来的预期也不能当作已经发生的事实。

课堂提出“把大语言模型当作编译器”的教学例子。模型根据原始材料提出记账动作。账本代码检查结构和约束。人工审核业务含义。多个报表再由同一组已检查的动作计算。

教学示例： 支出 75 元，利息收入 22.07 元，货币资金净变化为 22.07 − 75 = −52.93 元。不应让模型分别猜测每张报表的数字。

重放可以重新计算内部视图，不能再次付款、发通知或扣费。要复现某个历史结果，系统还须保留当时使用的规则版本和外部输入。

编者说明： 事件溯源把事实、视图和预期分开，但不消除本质复杂性。主要问题从修补多份状态，转向正确计算和管理历史。它也不会自动发现全部依赖关系。

11. 教务系统：让结论保留依据

课程观点： 学生记录可能包括成绩、已通过课程、总学分、分类学分和毕业结论。这些数据不能都被当成可以独立修改的事实。

成绩记录和课程替代审批可以作为输入事实。规则从这些输入计算已通过课程，再按适用培养方案计算学分。毕业资格还要汇合其他条件，不能只看学分。

计算过程应当可以检查：

  1. 记录选课、成绩、认定和审批事实。
  2. 按替代和去重规则计算已通过课程。
  3. 按培养方案版本计算各类学分。
  4. 分别检查毕业设计、资产归还、政策和审批条件。
  5. 汇合各项条件，生成带输入引用的结论。

成绩更正应触发当前派生结果的重算。历史审核结论应保留当时的输入和规则版本；新计算可以将它标为待复核，但不能静默覆盖。审批记录应说明对象、范围和理由，不能把某门课的豁免扩展成所有条件都通过。

编者说明： 满足课程条件，不等于满足全部毕业条件。没有依据的“已批准”字段会隐藏依赖关系。缓存的计算结果需要明确的失效规则和重建方式。

12. 从状态一致性到计算正确性

课程观点： 课堂批评把许多派生字段当成独立值保存的做法，并用“十亿美元级错误”强调它的代价。

编者说明： 这是课堂修辞，不是数据库领域的正式缺陷名称。例如，成绩或培养方案变化后，一个独立保存的“可毕业”标记就可能过期。

SQL 可以表达查询、视图、约束和物化视图。更大的问题跨越数据库、应用逻辑、缓存和界面状态。系统必须明确这些部分之间的计算依赖。

MVVM、React、数据流系统和事件溯源处理不同层次的派生状态。它们不是同一种机制，但都让人追问：输入来源是什么？结果怎样从输入得到？

权威事实依据应保留重建派生信息所需的事实。缓存可以提高访问速度，索引可以提高查询效率，但它们都需要重建方式。必须由人作出的决定，应保存决定和依据。可以计算出的结果，应尽量保留为派生结果。

这种做法改变了主要风险。团队减少对多份快照的反复同步，转而检查计算是否正确。同样输入可以重跑，测试可以检查结果，审计可以追查依据。

编者说明： 系统仍需处理规则版本、时间边界、权限和外部副作用。“现在由过去计算而来”是可追溯原则，不是计算必然正确的保证。

任务分解：先确定共享契约

编者说明： 以下是对课程思想的应用，不是课堂原话，也不是 ASD-STE100 的规则。

  • 事实负责人：记录已接受的事实及其依据。
  • 规则负责人：定义业务规则及其版本。
  • 查询视图负责人：按事实和规则构建查询结果。
  • 测试负责人：检查接口、始终应成立的约束和典型计算。

每部分都要有明确的输入和输出。并行开发前，先确定共享字段、错误情况和可执行的验收样例。查询视图是派生结果，不是另一份独立事实。

术语表

  • 意图：希望解决的问题或达到的目标。
  • 规约：对程序行为、输入输出和约束的明确约定。
  • 实现：落实规约的程序及相关机制。
  • 本质复杂性：业务问题本身包含的困难。
  • 附带复杂性：表示和实现方式额外增加的困难。
  • 解空间：在共同约束下允许采用的一组方案。
  • 组合：按共同规则把多个能力连接起来。
  • 关系模型：用关系表达数据及其逻辑联系的模型。
  • 事务：将相关数据库操作作为一个工作单元处理的机制。
  • 模型：表达领域知识和业务操作的部分。
  • 视图：向使用者呈现数据和结果的部分。
  • 控制器：接收输入并组织业务调用的部分。
  • 界面状态：影响展示和交互的状态。
  • 视图模型：组织展示状态和行为的对象。
  • 派生状态：由其他输入按规则计算出的结果。
  • 数据依赖：某个结果需要哪些输入的关系。
  • 事实记录：系统已接受的业务记录，仍需来源和权限依据。
  • 事件：表示已经发生之事的记录。
  • 命令：对系统提出的期望动作。
  • 持久历史：保存后可供查询或重放的历史记录。
  • 重放：重新处理已有事件，计算内部状态。
  • 归约器：按规则依次处理事件、计算状态的程序。
  • 投影：从事实计算出的特定视图。
  • 权威事实依据：在明确领域内，其他结果所依赖的事实来源。
  • 规则版本：标识一组确定规则的版本。
  • 外部副作用：付款、发通知等改变外部世界的操作。
