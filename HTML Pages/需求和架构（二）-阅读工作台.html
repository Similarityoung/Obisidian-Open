01

复杂性：架构从十行开始

需求工程收缩意图空间，架构设计收缩规约与实现空间。

从汉诺塔、二维码生成器到教务系统，规模不同不等于没有架构。只要代码替我们做了决定，未来就被推向某些方向。一个“先让它跑起来”的实现也会留下技术债：数据怎样表示、规则放在哪里、入口如何调用，都会影响下一次修改。

需求从 intent 到 specification 再到 implementation，不是唯一翻译路径。“让学生方便地选课”可以变成先到先得、志愿排序或抽签。选定规约之后，仍然有多种数据结构、模块边界与交互方式。每一个未确认的决定，都是实现偏离意图的机会。

本质复杂性来自问题本身。课程有容量、先修课、时间冲突和特批。换成纸笔，这些约束依然存在。附带复杂性来自表达方式：同一份学生信息保存五次、日期格式各自不同、规则复制在多个页面，都是组织软件的方式额外制造的麻烦。

需求工程要把真正的业务约束说清楚，但承诺越多，测试和维护的成本越高。架构不能让先修要求消失，却可以让资格、容量和时间冲突各自有清楚的归属，让学生选课、管理员补选和批量导入调用同一套规则。判断架构是否帮忙，可以先问：需求改一处，系统要跟着改几处？

空间问题设计动作
Intent客户究竟要什么？用例、边界、例外和验收条件收缩歧义。
Specification规则如何表达？给易变决策分配明确的模型和接口。
Implementation代码如何落地？隐藏存储和表示细节，减少重复同步。
读法：不要把“架构减少复杂性”理解成删除业务规则。它减少的是重复、猜测、泄漏和无来源的派生状态。
02

尊重小脑袋：抽象与层次

人不能一次追踪整个程序，设计要把不可掌握的整体变成可逐层检查的结构。

Dijkstra 的提醒很直接：人的头脑很小，最好承认限制并设计给它使用。枚举帮助检查有限分支，归纳帮助理解循环与递归，抽象让调用者只依赖承诺的效果，不必每次展开内部过程。

“珍珠项链”比喻强调，每颗珍珠承载一个设计决定，上层使用下层提供的概念。如果两种实现遵守同一接口，就有机会替换其中一颗，而不牵动其余部分。重要的不只是切了多少模块，更是何时做表示决定。

一幅图像如果过早被解释成“一行一行”，后续层都必须理解“行”。延后这个决定，中间层仍可按“图像”思考。表示细节传播得越远，变化牵动的范围通常越大。

类把数据和操作组织成概念，对象保留自己的状态。子程序用调用与返回表达控制流，协程则可以保存执行位置、交替恢复，适合两个地位对等的程序互相推进。抽象的价值不是增加名词，而是减少同一时间必须记住的东西。

枚举检查有限的分支和边界。
归纳解释重复、循环与递归。
抽象只依赖接口承诺的效果。
展开：概念层次为什么有用
可以先让双向链表提供连接操作，再在其上构造离散事件模拟，最后用“请求机器、加工、释放机器”的词汇描述车间。每一层让使用者忘记上一层的一批细节，但不能破坏底层的约定。
03

解空间：设计可以继续生长的规则

好的架构不是选出唯一终局，而是固定协作规则，同时保留合理的局部选择。

一个好名字可以承载已经理解过的知识。程序员说“事务”“队列”“选课资格”时，不必重新展开全部实现。Steele 的 Growing a Language 把这种能力演成一次语言生长：语言很小，容易移植，却可能无法表达真实工作；语言一次做得太大，又可能在成功前被替代。

可生长的设计不靠预言所有功能，而是让扩展成为一等公民，并且可以组合。今天确定数据交换规则，未来仍可增加处理步骤；今天固定业务对象接口，未来仍可替换实现。设计者要明确哪些协作规则不能破坏，哪些选择可以交给后来者。

“解空间”不是拒绝决策的借口。若接口、语义、权限和错误处理都没有确定，使用者得到的不是开放空间，而是不可靠的猜测。开放必须建立在稳定契约上。

判断句：看一个架构时，问它固定了什么、开放了什么、谁可以扩展、扩展如何组合、违反约定时如何失败。
展开：把经典读成设计判断
不要只问“它为什么经典”。对原文逐层追问：这一层新引入了什么概念？调用者因此不用关心什么？哪些操作会破坏底层假设？再用自己的系统对照这些问题。
04

UNIX：组合规则比现成用途更有力量

工具能否协作，不只取决于各自做好一件事，还取决于共同协议。

UNIX 常被概括为：每个程序做好一件事；让程序协作；处理文本流，因为文本是一种通用接口。第三条让前两条真正可用。一个工具的输出可以给人读、保存到文件，或者交给下一个工具；流水线中间也可以被截取和检查。

“都是文本”还不够。选项和操作数如何区分、数据和诊断写到哪里、成功与失败如何报告，都要有约定。标准输入承载输入，标准输出承载正常结果，标准错误承载诊断，退出状态另行表示执行结果。分隔符也是协议的一部分，文件名含换行时，简单按行切分就可能失真。

jq 提取 JSON 字段，fzf 让人从候选项中选择，xdotool 把窗口操作变成命令。设计者不用提前实现所有书目管理或窗口管理需求，只需提供可以组合的规则，使用者就能创造新的用途。

输入stdin：可读、可保存、可交接。
处理一个工具只承担清楚的职责。
输出stdout / stderr / exit status 分离。
展开：组合协议检查表
在脚本接入一个新工具前，确认编码、字段、分隔符、排序规则、退出码、错误输出和版本变化。可组合性来自细节，而不是“大家都输出字符串”这句口号。
05

关系数据库：把意义与存储分开

关系模型让应用表达逻辑关系，让数据库负责索引、页面和执行计划。

Codd 的关系模型希望保护数据使用者，使他们不必因为数据量增长和访问模式变化而重写使用方式。应用描述读者、书和借阅关系；它可以按读者查询借了哪些书，也可以按馆藏查询被谁借走。索引、数据页和扫描顺序属于另一个层次。

SQL 是一门带语义和组合规则的语言。查询表达要得到什么，优化器选择怎样执行，事务把需要整体处理的读写组织成一次状态变化，视图则给当前世界一个可查询的切片。数据库因此提供了一个可持续生长的应用基础。

关系数据库不会自动理解业务。它可以约束字段、协调更新，却不能替团队决定“课程通过”是否等于“满足毕业要求”，也不能替团队处理时间、权限和例外。逻辑关系被定义之后，数据才能真正获得独立演化的空间。

现实读者借走某册书。
关系读者 · 馆藏 · 借阅。
存储索引、页面、执行计划可替换。
06

Internet：在持续变化中保持协作

分层让局部替换成为可能，共同接口让整体仍能运行。

Internet 只需先解决连接问题，不预设上面会运行哪一种应用。应用提出请求，传输层提供相应的交付性质，IP 层跨网络传递数据报，链路层负责相邻设备。应用不必知道每段链路使用什么硬件。

RFC 1958 把持续变化视为架构事实。网络路径和设备会变化，但共同协议让局部替换与整体延续同时发生。TCP 的拥塞控制、连接管理等细节很难，却都服务于通用通信抽象。

Telnet 到 SSH、FTP 到更安全的访问方式、HTTP 到 HTTPS，展示的是在共同规则上替换局部。分层不是越多越好：只有当职责会独立变化时，层次才值得承担其沟通成本。

边界：“变化本身会持续”不等于“每个模块都要抽象成平台”。先证明变化会独立发生，再决定边界。
07

从一个页面一段 SQL 到 MVC

当页面、规则和数据库变化不同步时，关注点分离为变化提供归属。

早期业务系统可以把每个功能映射成一个数据库事务：读课程、检查能否选、写选课记录、返回页面。数据库视图把当前状态切成一个页面。这种结构对局部、稳定的 CRUD 很有效。

风险来自规则复制。学生选课页、管理员补选页、批量导入都可能各自检查容量。JSP、JSTL 和表达式语言改善了页面生成，却不会自动把业务规则放入正确位置。

MVC 提供一种关注点分离：Model 表示当前领域知识和业务操作；View 是 Model 的一种呈现；Controller 把用户输入翻译成对 Model 的调用。课表从列表改成周历，主要改 View；容量规则变化，应该改 Model；新增入口，则复用 Model 能力并检查权限。

Controller接收输入，组织一次请求。
Model拥有事实、规则和业务动作。
View把结果投射成用户看到的形式。
展开：MVC 的边界不是文件夹名
MVC 是关注点分离的设计思想，不是一套固定目录。真正要问的是：规则是否只有一个归属，展示变化是否不必触碰业务，入口是否复用相同业务能力。
08

界面状态：MVVM 与 React

界面也有状态；把派生关系写出来，比在回调里藏同步更容易检查。

搜索词、展开菜单、hover 高亮、选中的标签，不一定要写进业务数据库，但它们仍然影响程序。可以用 View = render(Model, ViewState) 表达：界面是业务状态和界面状态共同渲染的结果。是否持久化，和是否值得建模，是两件事。

MVVM 把展示状态与行为组织进 ViewModel。课程筛选可以只保存 query，把 visibleCourses 作为课程列表和查询词的派生结果。Vue 的 computed 追踪依赖，v-model 把控件值与输入事件的两条连接包起来。

React 用当前属性和状态描述一次 render。输入事件触发状态更新，下一次 render 得到新的状态快照。派生列表不必再存一份 State。React 和 MVVM 讨论的是相近的依赖问题，但两者不是同一个机制；不要把框架名称当成架构结论。

状态例子推荐处理
源状态课程数据、query明确保存，作为计算输入。
派生状态visibleCourses由源状态计算，避免重复存储。
瞬时界面状态hover、展开菜单认真建模，但不必持久化到业务库。
09

长流程：把复杂性放进 Model 还不够

长时间、强规则、跨步骤的业务会让一个 status 字段背负过多历史。

MVC 和 CRUD 擅长一次完成一小段局部操作。订单却可能经历下单、锁库存、优惠、支付、风控、发货、退款、售后和对账。教务系统也有学分、毕业设计、资产归还、政策例外和审批记录。

最直接的做法是放一列 status，或堆叠一组“是否完成”。这种状态看似简洁，却没有说明当前值从哪些事实推来。错误、手工覆盖或漏更新会使记录同时表示“能毕业”和“不能毕业”，形成静默损坏。

根源不是状态机这个词，而是把过去、现在和未来压进一张当前快照。若一门先修课从通过改为不通过，相关课程、学分和毕业结论都可能受影响。直接修改快照，必须找到每一份受影响的副本。

选择边界：简单维护功能仍可采用 CRUD。只有历史、审计、重放或依赖分析确实有价值时，才值得承担事件溯源的存储和运维成本。
10

过去、现在与未来：从事实重建状态

过去是已经发生的事实，现在是按规则得到的视图，未来是尚未发生的预期。

复式记账用同额、相反方向的分录保持资产等式。它能发现一部分不一致，却不保证业务分类正确：金额相等的错误分录也可以平衡，原始凭证和业务含义仍需审查。

事件溯源不把当前状态当作唯一事实，而保存状态迁移的历史。事件记录发生了什么；命令表达希望做什么；归约器按规则把事件重放成当前视图。发生错误时追加更正、撤销或冲销，而不是悄悄抹去历史。

课堂中的 “LLM as a Compiler” 是教学例子：模型把原始材料翻译成有限的记账动作，确定性的账本代码执行约束，人工检查业务含义。模型不能逐格填写报表并假设数字天然一致。

重放可以重新计算余额，但不能再次付款、发通知或扣费。要复现当时结果，还必须保存规则版本、业务生效时间和外部输入版本。事件溯源改变的是问题形状，不是消除本质复杂性。

11

教务系统：让毕业结论可追溯

把事实、规则和派生结果分开，结论才有计算路径。

成绩记录、已修课程、总学分、分类学分和“是否满足毕业条件”不应都作为可以独立修改的事实。若成绩更正后只更新其中几项，系统就会同时存在几个互相矛盾的“现在”。

更稳妥的依赖链是：选课、成绩、认定和审批记录作为输入；按去重、替代和分类规则计算已通过课程；按培养方案版本计算各类学分；再分别判断毕业设计、资产归还、政策特例和审批条件；最后生成带输入引用的毕业结论。

“课程条件满足”不能悄悄变成“所有毕业条件满足”。特例必须记录对象、范围、审批者和依据。结论可以缓存，但必须知道它何时失效、怎样重建、为什么改变。

    从状态一致性到计算正确性

    保存足以重建其余信息的事实依据，让派生结果可以重跑、测试、审计。

    把 can_graduate = true 当成独立事实很快会过期。SQL 当然能表达查询、视图、约束和物化视图。这里真正的问题更宽：数据库、应用逻辑、缓存和界面之间的计算依赖，谁负责更新，谁知道失效，谁能解释来源？

    MVVM、React、dataflow 和事件溯源处在不同层次，机制也不同，但都可以帮助我们提出同一问题：源是什么，结果怎样从源得到？把不同模式并列，不是说它们都由 SQL 的某个缺陷直接产生。

    系统应保存足以重建其余信息的事实依据。缓存、汇总和索引可以为性能存在，但要有失效规则和重建路径。必须由人作出的决定，应保存决定与依据；可以计算出的结果，尽量不要再引入一份无来源的独立副本。

    复杂性不会消失，只是从“如何让许多份状态永远相等”转移为“这段计算是否正确”。给定输入可以重跑，测试可以检查，审计可以查看，依赖图可以分析。对生成式软件工程而言，这让 AI 生成和人工检查拥有共同对象：每个重要结果都应能回答“我是怎样算出来的？”

    最后的验收问题：如果一条基础事实改变，系统能否列出受影响的结果？能否使用当时的规则和外部输入复现？能否证明不会重复执行外部副作用？

    复盘：用自己的话回答

    1. 为什么“分模块”本身不等于减少复杂性？

    因为模块只有在隐藏了会变化的决定、拥有清楚接口、并被多个入口复用时，才减少重复猜测和同步成本。

    2. 事件溯源保存的是什么？它没有自动解决什么？

    它保存已发生的事实并由事实重建视图；它没有自动解决领域规则、规则版本、外部输入、权限或计算错误。

    3. React、MVVM 和事件溯源可以直接互相替换吗？

    不可以。它们处理不同层次的依赖：界面派生状态、展示模型组织、业务历史与状态重建。
